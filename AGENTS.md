# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Cursor, Aider, etc.) working in this repository.

## What this repo is

A [BlueBuild](https://blue-build.org/) recipe that produces a signed OCI image (`ghcr.io/quin7ilian/bluefin-gdx-workstation`) layered on top of `ghcr.io/projectbluefin/bluefin-lts-nvidia:stable` for an HPO/ML workstation. The output image retains its legacy GDX-derived name for registry continuity. There is no application code — the deliverable is a bootable container image. `recipes/recipe.yml` is the canonical source of truth for what the image contains.

## Build & test

Builds run in CI only: `.github/workflows/build.yml` invokes `blue-build/github-action@v1.11` against each entry of the `matrix.recipe` list. To trigger one, push to the branch (the workflow ignores `**.md` changes), open a PR, or use **Actions → bluebuild → Run workflow**. There is no local build loop on Windows — to iterate locally you need a Linux host with `bluebuild` installed and would run `bluebuild build recipes/recipe.yml`. Verification is post-deploy on the target machine — e.g. `swapon --show` (expect no output), `cat /proc/cmdline | grep nvidia-drm.modeset`, `nvidia-smi`, `sysctl vm.dirty_bytes`, `ls /dev/ipmi*`, `systemctl status coolercontrold`.

## Architecture

- **`recipes/recipe.yml`** — top-level declarative pipeline. The `modules:` list runs in order. Four module types are used here:
  - `files` — copies `files/system/**` onto `/` in the image (so `files/system/etc/sysctl.d/foo.conf` lands at `/etc/sysctl.d/foo.conf`).
  - `script` — inline bash run in the build container; this is where third-party repos are added and `dnf install` runs.
  - `kargs` — writes `/usr/lib/bootc/kargs.d/` entries that bootc applies on `bootc upgrade`. The dedicated module, **not** `rpm-ostree: kargs:` (that property was removed from the rpm-ostree schema when LTS moved to bootc; using it fails recipe validation).
  - `signing` — wires up cosign signing using `SIGNING_SECRET` from repo secrets; the public key is `cosign.pub` at the repo root.
- **`files/system/`** — mounted to `/` at build time. Put OS config here (`etc/sysctl.d/`, `etc/systemd/`, `etc/tmpfiles.d/`, `etc/modules-load.d/`, `usr/share/ublue-os/just/`, etc.) rather than `cp`ing files inside a `script` module.
- **`files/scripts/`** — referenced from script modules when a snippet grows past a few lines. Currently only contains the BlueBuild example.
- **`modules/`** — empty; reserved for custom BlueBuild modules. Don't add files here unless you're authoring a new module type.

## Hard constraints

These will silently break builds or runtime behaviour if violated. Each has been verified empirically — don't re-derive.

1. **Base is CentOS Stream 10, which ships dnf4, not dnf5.** The BlueBuild `dnf` module requires dnf5 and fails with `Main dependency 'dnf5' is not installed`. Use `type: script` with `dnf install -y …` for all third-party RPMs.
2. **Bluefin LTS has no rpm-ostree package layering at runtime.** Every host RPM the user needs must be baked in at build time; upstream Developer Mode installs optional user-facing tools through Homebrew/Flatpak instead. Notes on kargs: the BlueBuild `rpm-ostree` module's `kargs:` property is no longer in the schema. For *new* kargs the dedicated `kargs` module works (writes to `/usr/lib/bootc/kargs.d/`, applied by bootc). For *overriding* kargs that the base image already sets (e.g. Bluefin LTS NVIDIA ships `/usr/lib/bootc/kargs.d/00-nvidia.toml` with `nvidia-drm.modeset=1`), a second kargs.d file does NOT win — bootc upstream documents cross-file karg removal/override as "currently undefined behavior" and the base value empirically wins on `/proc/cmdline`. Override by editing the base file in place from a `script` module (sed with grep-assertions that fail the build if the base changes shape) — see the `nvidia-drm.modeset` override in `recipes/recipe.yml`.
3. **`/usr` is read-only at runtime; `/etc` is writable.** Drop persistent config in `/etc/…` via `files/system/etc/`.
4. **No swap, ever.** This is a 512GB-RAM workstation; OOM killer is the desired failure mode. Override `/usr/lib/systemd/zram-generator.conf` with an empty file at `/etc/systemd/zram-generator.conf` — do not add swap files, swap partitions, or zram configuration.
5. **Insync: install the `insync` GUI + `insync-nautilus` from the native EL10 repo** (`https://yum.insync.io/centos/10/`). The upstream RPM does not ship a systemd unit; we provide a user-level one (`files/system/usr/lib/systemd/user/insync.service`) that runs `insync start --no-daemon` with `Type=simple` — foreground process, journal-tracked. (An older version of this unit used `insync --synchronous-full start` with `Type=forking`; that top-level flag was removed sometime before 3.9.10 and now fails at boot with "Error: No such option: --synchronous-full". Do NOT reintroduce it.) After first GUI launch, the user must uncheck "Start Insync at startup" in Preferences to avoid a duplicate-launch race against the systemd unit.
6. **CUDA/Podman/CDI config comes from the Bluefin LTS NVIDIA base; don't recreate it or bake Docker/dev tools into this image. The Nvidia *graphics* stack is deliberately stripped for compute-only — do NOT revert it to "just the karg".** `nvidia-drm.modeset=0` is necessary but **NOT sufficient**: it only stops nvidia driving a *display*, while `nvidia_drm`/`nvidia_modeset` still register the compute cards as DRM devices (`/dev/dri/cardN`, `/dev/nvidia-modeset`) that GNOME/Mutter/Electron enumerate and hold open via EGL/GLX/Vulkan, wasting the GPUs and introducing unwanted cross-GPU paths. Enforcing compute-only takes **five** coordinated mechanisms — the `nvidia-drm.modeset=1`→`=0` base-karg edit (see #2), plus the four in the "Make the Nvidia cards COMPUTE-ONLY" script module of `recipes/recipe.yml` together with `files/system/usr/lib/modprobe.d/nvidia-compute-only.conf`: (1) modprobe **`blacklist`** + `install … /usr/bin/true` on `nvidia_drm` and `nvidia_modeset`; (2) strip all nvidia modules from the base dracut `force_drivers` (`/usr/lib/dracut/dracut.conf.d/99-nvidia.conf`); (3) disable the Nvidia Vulkan ICD (`nvidia_icd*.json` → `.disabled`); (4) regenerate the initramfs while explicitly omitting `nvidia`, `nvidia_drm`, `nvidia_modeset`, `nvidia_uvm`, and `nvidia_peermem` (dracut does not treat a bare `nvidia` value as a substring glob). CUDA is unaffected — `nvidia` + `nvidia_uvm` remain in the real root and load on demand. The recipe also asserts the host CUDA packages, `libcuda.so.1`, module presence, and kernel/userspace driver version match. Verify after rebase: `lsmod | grep -E 'nvidia_drm|nvidia_modeset'` empty and `nvidia-smi` plus a Podman CDI CUDA test work.
7. **CoolerControl: install `coolercontrold` only from the COPR** (`codifryed/CoolerControl`, `epel-10-x86_64` chroot — the COPR `.repo` file is self-contained and does NOT require enabling EPEL). The Qt `coolercontrol` desktop wrapper RPM is unnecessary: the daemon serves a web UI on `http://localhost:11987`. Use `--setopt=install_weak_deps=False` to skip the `python3-liquidctl` Recommend (would otherwise pull EPEL; we have no liquid cooling). `ipmi_si` + `ipmi_devintf` are autoloaded via `files/system/etc/modules-load.d/ipmi.conf` so `/dev/ipmi0` is available for `ipmitool`. **`ipmi_si` is also pinned to KCS at I/O port `0xca2` via `files/system/etc/modprobe.d/ipmi.conf`** — without that, the kernel relies on DMI Type 38 auto-discovery, which the BIOS sometimes doesn't populate when POST races ahead of BMC readiness on cold (AC-cycled) boots. Symptom: `ls /dev/ipmi*` returns nothing, `dmesg` says `ipmi_si: Unable to find any System Interface(s)`, and `dmidecode --type 38` returns empty. Hard-coding the KCS port bypasses the race. **`cc-plugin-custom-device` is installed post-rebase via `ujust install-cc-plugin`, NOT at build time** — coolercontrold 4.x migrates `/etc/coolercontrol/plugins` to a symlink to `/var/lib/coolercontrol/plugins` on first start, and a build-time install bakes the path as a directory, producing an unrecoverable ostree `/etc` merge conflict ("Modified config file newly defaults to directory 'coolercontrol/plugins', cannot merge") on every subsequent deployment. Channel configuration (per-fan PWM commands, temp-sensor read commands) is read by the plugin from `/etc/coolercontrol/plugins/custom-device/config.json` (JSON, schema in `cc-plugin-custom-device/src/config.rs`: `devices[].channels[].commands` and `devices[].temps[]`). The plugin's `manifest.toml` is just a *service* manifest (how to run the plugin process); the real channel definitions are in `config.json`. **We ship a pre-populated config.json template** at `/usr/share/cc-bmc-bridge/config.json` and `ujust install-cc-plugin` copies it into place (skip-if-exists) so users don't have to type 19 shell commands into the UI. Channels are 7 fans + 12 temps; see `/usr/share/cc-bmc-bridge/channels-reference.md` for the mapping. Commands run via `sh -c`; temp values >1000 are auto-divided by 1000 by the executor (millidegree fallback). **The plugin's `manifest.toml` MUST have `privileged = true`** — upstream ships `false`, which makes the plugin run as the unprivileged `cc-plugin-user` who can't read `/dev/ipmi0`. Symptom: temps don't populate in CoolerControl's UI, channels show no RPM, fan writes silently fail. `ujust install-cc-plugin` flips this with `sed` (idempotent); `ujust upgrade-cc-plugin` preserves the local setting via backup/restore around upstream `install.sh`. If you see `ps aux | grep custom-device` showing `cc-plug+` as the owner instead of `root`, the flip didn't happen and you need to `sudo sed -i 's/^privileged = false$/privileged = true/' /etc/coolercontrol/plugins/custom-device/manifest.toml` + `sudo systemctl restart coolercontrold`. Do NOT replace this with a custom file-sensor + glue-script architecture — the plugin supersedes that pattern. Do NOT move the plugin install back to build time.
8. **BMC fan-control bridge for CoolerControl.** A companion `coolercontrol-bmc-bridge.service` (oneshot, `BindsTo=`/`WantedBy=coolercontrold.service`, `Before=coolercontrold.service`) flips FAN1-7 to BMC manual mode before coolercontrold starts and back to default on stop — so the BMC's auto-curve is the failsafe if CoolerControl crashes or is stopped. **The upstream `coolercontrold.service` is NOT modified.** The bridge talks to the BMC via the ASRock Rack OEM IPMI command set: `0x3a 0xda` reads the current 16-byte duty register, `0x3a 0xd6 <16 bytes>` writes it, `0x3a 0xd8 <16 bytes>` sets per-fan mode (0x00 = default, 0x01 = manual). Per-channel writes from CoolerControl go through `/usr/libexec/cc-set-fan-duty.sh <idx 1-7> <duty 0-100>`, which does the read-modify-write of the 16-byte duty register (the only write path the BMC supports). The wrapper has a hard floor of 5% on requested duties — this is a **BMC-validation floor**, not a thermal-safety floor (the BMC rejects writes containing `0x00`/`0x01` with `0xcc "Invalid data field"`, and 5% also keeps fans above their physical stall threshold in practice). Thermal safety is the user's responsibility via CoolerControl curves. The wrapper also hard-codes positions 8-16 of the 16-byte payload to `0x05` because unused FAN slots there trigger the same `0xcc` rejection. **Iteration 2 (2026-05-28) added FAN6 (SB_FAN1, chipset) and FAN7 (MOS_FAN1, VRM) to CoolerControl** — they were the noisiest fans on the system at the BMC's default duties (30%/60% → 2300/5400 RPM on tiny high-RPM fans). Wrapper `fan_idx` validation widened to 1-7. `silent-curves-reference.md` specifies floors of 20% (chipset) and 30% (VRM) with aggressive ramp-up past 70°C — do NOT lower these floors without validating VRM thermals under sustained AVX-512 load (TR Pro can pull 280W+ sustained; VRM failure under load is silent and expensive). The bridge's `ExecStop` reverts FAN1-7 to BMC default on coolercontrold stop/crash, so BMC's own thermal protection remains the failsafe for the board fans. Liquidctl integration is disabled via `ujust disable-liqctld` (sed-edits `liquidctl_integration = false` into `/etc/coolercontrol/config.toml`) — `ujust install-cc-plugin` calls this automatically; it's idempotent. Fan-index → physical mapping (verified empirically 2026-05-28): `1=CPU_FAN1, 2=CPU_FAN2/WP (rear), 3=CHA_FAN1/WP (bottom hub), 4=CHA_FAN2/WP (top front), 5=CHA_FAN3/WP (bottom front), 6=SB_FAN1 (chipset), 7=MOS_FAN1 (VRM)`. **The BMC fan-mode setting is sticky across reboots** — that's why the bridge's `ExecStop` reverts to default mode, so a system rebooted out of the bridge's lifecycle (e.g. bridge masked, coolercontrold disabled) doesn't leave fans stuck in manual at last-written values.
9. **amdgpu high-refresh blanking on Navi 33 + G95SD — panel runs 5120×1440@120 with a big vblank; 240 Hz is a hardware wall.** The W7500 driving the G95SD blanks intermittently on cursor/plane updates: the amdgpu memory-clock (UCLK) switch can't hide in the vblank. **NOT PSR** (sink advertises PSR ver 0, `journalctl -k | grep -i psr`). **The ROOT fix is an enlarged vertical blank, NOT DSC state:** native 120 Hz's ~459 µs vblank is too short for the switch (60 Hz is clean because at half the pixel rate it fits its ~461 µs), so the custom EDID stretches Vtotal to 1650 (~1060 µs) to give the switch room. The vblank *duration* is set by the mode timing and is **independent of DSC** — the switch hides whether DSC is on or off; confirmed no-blank across a reboot at both 8bpc (driver runs HBR3 0x1e + light DSC, `dsc_clock_en=1`) and 10bpc/HDR. **Fix = `drm.edid_firmware=DP-1:edid/g95sd-120.bin`** alone (in `/usr/lib/bootc/kargs.d/15-amdgpu-edid.toml`; EDID pulled into the initramfs by `.../dracut.conf.d/99-amdgpu-edid.conf`, amdgpu is force-loaded early). **DSC is left ENABLED** so HDR / 10-bit is available on demand (GNOME Settings → Displays → HDR). **ROLLBACK:** if the intermittent blank ever returns, add `amdgpu.dcdebugmask=0x4` (DC_DISABLE_DSC) to force 8bpc uncompressed over HBR3 (~25.3 < 25.92 Gbps) — the most-proven no-blank config, but it blocks HDR/10-bit (both need DSC's bandwidth). (`dcdebugmask=0x4` shipped in commit d00c267 and was dropped once the big vblank proved it hides the switch with DSC on.) **240 Hz is physically unfixable on this GPU:** 5120×1440@240@8bpc (~44 Gbps) exceeds the W7500's DP 2.1 **UHBR10 output ceiling of 38.8 Gbps** (AMD's datasheet — ignore retail "UHBR20/80" claims), and the panel's inputs are DP 1.4 + HDMI 2.1 (40 Gbps FRL5) anyway, so 240 *always* needs DSC in a tiny vblank. Also: **the panel only accepts its native refresh rates (240/120/60)** — custom rates like 216/200 get "Mode not Supported" — but it accepts a native refresh with extended blanking (VRR envelope). **A DP→HDMI 2.1 adapter does NOT help** (earlier escalation idea, disproven): every shipping active adapter has a DP 1.4 / HBR3 input (Synaptics VMM7100 / Realtek RTD2173), so it trains down to 25.92 Gbps — the same bottleneck as the monitor's own DP port. The only real 240 paths are **(a)** a native-HDMI-2.1 GPU to reach the monitor's 40 Gbps HDMI input — a single-slot Intel Arc Pro B50 (GUNNIR variant has 2× HDMI 2.1) is the candidate, **but Battlemage has an unresolved half-refresh-on-Wayland Xe bug (drm/xe #4363, no X11 escape on Bluefin), so NOT recommended yet**; or **(b)** a monitor with a native DP 2.1 UHBR13.5+ input (8bpc@240 uncompressed). Build the EDID from the stock EDID with the @240 and native-@120 DisplayID Type-I timings replaced by the big-vblank @120 (preferred), 60 Hz kept; craft/validate with `edid-decode` in a fedora `podman` container (not the CS10 host) and recompute all four checksums (base, CTA, DisplayID-internal @byte 382, EDID-block-2 @383); see `scratchpad/craft_120.py`. **Supersedes `amdgpu-pin-mclk.service`** (removed — recover from git history), which fixed the blank only by writing `manual` to `power_dpm_force_performance_level`, clamping SCLK to ~810 MHz → sluggish desktop. **Verified NON-fixes, do not retry:** anything at 240 Hz (bandwidth wall — UHBR10 output cap); custom non-native refresh rates (panel rejects with "Mode not Supported"); DP→HDMI adapters (DP 1.4-input bottleneck); `amdgpu.ppfeaturemask` (doesn't map to RDNA3 SMU flags); `dcdebugmask=0x410` (no PSR); `0x20`/force-SubVP (didn't hide the switch here).
10. **Profiling tools must be host-installed, not Distrobox-installed.** `perf` and `bpftrace` are built from the kernel source tree and must match the running kernel's ABI; a Distrobox ships them built for a different kernel and produces cryptic errors, miscounted events, or unresolved symbols. Same for ftrace consumers and anything reading `/sys/kernel/debug`. Userland Python profilers (`py-spy`, `scalene`, `austin`, `memray`, etc.) read process memory rather than kernel counters and don't have this constraint — those go in the conda env, not the recipe. The host profiling pack (`perf bpftrace sysstat strace ltrace numactl hwloc`) is all from CS10 AppStream/BaseOS.
11. **RPM-post-install groups for setgid IPC must be backstopped via `sysusers.d`.** The 1Password RPM's `after-install.sh` does `groupadd onepassword` + `groupadd onepassword-mcp` + `groupadd onepassword-cli` at build time, then `chgrp + chmod g+s` on `1Password-BrowserSupport` (GID 1001), `onepassword-mcp` (GID 1002), and the CLI (GID 1000). On a fresh `bootc` deploy, user creation grabs GID 1000 first — collision with `onepassword-cli` — and **ostree's `/etc` 3-way group merge silently drops the ENTIRE 1Password group block instead of just the colliding entry**. Result: `/usr/etc/group` has all three groups, `/etc/group` has none of them, and the 1Password daemon's `SO_PEERCRED` peer-group check on incoming IPC connections silently rejects everything because `getgrnam("onepassword")` returns NULL. Symptom: 1Password browser extension can't connect; **no SELinux denial, no journal entry, no error to grep for** — looks like the integration is just dead, costing an hour of false-lead chasing through manifests, sandbox theories, and policy files. Fix is `files/system/usr/lib/sysusers.d/1password.conf` with `g onepassword 1001 -` and `g onepassword-mcp 1002 -` (GIDs MUST match the build-time `chgrp` baked into the binaries — change them here and the SO_PEERCRED check fails again). We deliberately skip `onepassword-cli` because its build-time GID 1000 unavoidably collides with the local user; the CLI works without that group, just less hardened. Same trap pattern will hit ANY package whose post-install scriptlet does `groupadd` + setgid; if you add another such package to this image, ship a matching `sysusers.d` entry up front. **Existing deployed systems need a one-shot `sudo groupadd -g 1001 onepassword` (+ optional `-g 1002 onepassword-mcp`) and a 1Password app restart** — the sysusers.d file only fires on subsequent boots after `bootc upgrade`.

12. **Zed must come from the official upstream tarball** (current working URL: `https://zed.dev/api/releases/stable/latest/zed-linux-x86_64.tar.gz` — 307s to the corresponding GitHub release asset), not Terra (Fedora glibc mismatch), Flatpak (breaks client-side decorations), or Homebrew (cask is macOS-only). The tarball extracts to `zed.app/`. On Zed 0.139+ the previously separate `bin/cli` and `bin/zed` binaries were consolidated into a single `bin/zed` — `/usr/bin/zed` symlinks to it, and `.desktop Exec=` points at the same path.

13. **Use upstream `ujust devmode` for optional developer applications.** Do not reinstall old GDX's Docker, VS Code, Cockpit, compiler, or virtualization package set in the image. The retired Win11/libvirt/VFIO stack was deliberately removed: do not reintroduce host libvirt/QEMU packages, the qemu hook, VM kargs/templates, or the swtpm policy unless the user explicitly restores that use case.

## Working on the recipe

- Single `dnf install` transaction for all third-party packages in the same module is faster than per-package calls; keep `dnf clean all && rm -rf /var/cache/dnf /var/cache/yum` at the end of any package-installing script snippet to keep the image small.
- When adding kernel args, append to the existing `kargs` module's list rather than adding a second `kargs` module.
- The build is signed: `cosign.key` / `cosign.private` are gitignored; `cosign.pub` is committed and used by end users (`cosign verify --key cosign.pub …`).
- CI builds daily at 06:00 UTC (20 min after ublue upstream rebuilds), so the image picks up upstream Bluefin updates automatically.
- Each image rebuild also downloads the latest stable upstream Zed tarball.
- Day-to-day updates on the deployed system happen automatically via Bluefin's `uupd` daemon (6-hour timer, uses `bootc` under the hood). Manual on-demand update is `sudo bootc upgrade` then reboot — NOT `rpm-ostree upgrade`, which won't reliably re-apply `/usr/lib/bootc/kargs.d/` entries.
